# PQC 전환 계획: ch9 - OpenSSL SSL/TLS 클라이언트/서버 통신

## 1. 전환 목적

이 장은 [ch9/ssl_client.c](ssl_client.c)와 [ch9/ssl_server.c](ssl_server.c)를 통해 OpenSSL 기반 TLS 통신을 구현한다.

- `SSLv23_client_method()` / `SSLv23_server_method()`를 사용한다.
- `SSL_CTX_new()`로 컨텍스트를 생성한다.
- 공개키 인증서와 개인키를 로딩하고 TLS 핸드셰이크를 수행한다.

이 구조는 구형 SSL/TLS 구성 방식으로, RSA 기반 키 교환과 레거시 인증서 구조를 사용하므로 PQC 전환 대상이 가장 명확하다.

## 2. 현재 취약 암호 사용

- TLS 버전: 구형 SSLv23 API
- 키 교환: RSA 기반 또는 레거시 인증서 기반 구조
- 인증서: 로컬 PEM 인증서/개인키 파일
- API 관례: OpenSSL 1.0.2 계열 전용 구조

문제점:
- 구형 TLS 설정은 현대적 보안 요구를 만족하지 못한다.
- RSA 기반 키 교환은 양자 공격에 취약하다.
- 인증서와 키 관리 방식이 하이브리드 큐브 구조와 호환되지 않는다.

## 3. 전환 목표

- TLS 설정을 TLS 1.3 중심으로 전환
- 키 교환 및 서명 알고리즘에 PQC 알고리즘을 도입
- 인증서 체인과 개인키 로딩 로직을 양자내성 인증서 구조에 맞게 재설계

## 4. 5단계 전환 계획

### (1) 알고리즘/매개변수 설정

현재:
- `SSLv23_client_method()`, `SSLv23_server_method()`
- `SSL_CTX_new(meth)`
- 인증서 체인 로딩 및 개인키 로딩

전환 후:
- `TLS_method()` 또는 `TLS_client_method()` / `TLS_server_method()` 기반 설정
- PQC 호환 그룹을 지원하는 TLS 1.3 구성
- 하이브리드 키 교환 또는 순수 PQC 키 교환 알고리즘 선택

권장 방식:
- 서버와 클라이언트가 동일한 보안 정책 집합을 사용해야 한다.
- 기존 RSA 기반 인증서는 퇴역하고 PQC 인증서 체인으로 전환한다.

### (2) 키 준비

현재:
- `SSL_CTX_use_certificate_chain_file()`
- `SSL_CTX_use_PrivateKey_file()`
- 개인키와 인증서를 함께 로딩

전환 후:
- 양자내성 키 쌍과 인증서를 구성하고 로딩
- 키 식별 값과 알고리즘 ID를 함께 저장
- 공개키/개인키를 분리하여 보관하고, 민감한 개인키는 보호장치 사용

설계 포인트:
- 인증서 체인과 서명 알고리즘을 새 보안 정책에 맞게 업데이트
- 기존 CA 기반 구조를 유지하되 PQC 서명 알고리즘을 사용하도록 전환

### (3) 연산 초기화

현재:
- `SSL_library_init()`
- `SSL_load_error_strings()`
- `SSL_CTX_new()`에 메서드 등록

전환 후:
- TLS 라이브러리 초기화와 보안 프로토콜 선택을 현대 구조로 정비
- 하이브리드 키 교환 그룹 설정
- 서명 알고리즘 및 인증서 검증 규칙을 초기화 시점에 강제

중요 사항:
- TLS 1.3에서 핸드셰이크는 더 강한 보안 정책과 더 엄격한 알고리즘 선택을 요구한다.
- 구형 API 사용을 완전히 제거해야 한다.

### (4) 연산 실행

현재:
- `BIO_do_connect()` / `BIO_do_handshake()`
- 요청 전송 및 응답 수신

전환 후:
- PQC 하이브리드 키 교환 방식으로 핸드셰이크 수행
- 세션 키 생성 및 암호화/무결성 설정을 최신 표준에 맞게 구성
- 절차상 에러 관리와 보안 실패 분리를 강화

권장 사항:
- 가장 중요한 것은 핸드셰이크 단계에서 키 교환 알고리즘이 서로 일치하는지 검사하는 것이다.
- 보안 정책 불일치 시 연결을 즉시 중단해야 한다.

### (5) 결과 처리

현재:
- HTTP 응답 전송과 종료
- 에러 메시지 출력

전환 후:
- 연결 성공/실패 및 알고리즘 선택 결과를 로깅
- 인증서 검증 결과와 키 교환 알고리즘을 기록
- 에러 시 보안 이벤트 로그를 남겨 운영자가 원인을 추적 가능하게 함

권장 결과 처리:
- 보안 정책 오류, 인증서 불일치, 핸드셰이크 실패를 구분해 처리
- 실제 운영 환경에서는 로그와 자동 경보를 연결한다.

## 5. 적용 우선순위

1. TLS 1.0/1.2 레거시 방식 제거
2. RSA 기반 키 교환 및 서명 방식 교체
3. PQC 인증서 및 키 로딩 구조 정비
4. TLS 핸드셰이크와 보안 이벤트 로깅 개선

## 6. 요약

이 장은 가장 대표적인 네트워크 보안 예제로, PQC 전환의 가장 큰 영향이 발생하는 지점이다. ch9는 단순한 예제 코드가 아니라 “네트워크 보안 프로토콜 전반”을 보여주기 때문에, TLS 레벨의 전환을 어떻게 설계할 것인지가 가장 중요하다. 즉, PQC 전환은 코드 변경뿐 아니라 TLS 보안 정책, 인증서 체인, 핸드셰이크 알고리즘 설계를 함께 바꾸는 작업으로 이해해야 한다.
